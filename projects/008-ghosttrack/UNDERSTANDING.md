## 十二项摘要

### 定位

GhostTrack 是 Python 命令行查询集成工具：提供菜单、输入、函数调度、接口与库调用、终端展示；核心能力依赖现成服务、号码规则库和公开网页。

### IP 归属能力

输入已知 IP，调用 ipwho.is 返回国家、地区、城市、近似经纬度、ASN、网络组织、ISP 与时区；查询数据库关联记录，不能确认设备 GPS、具体住址或人的实时位置。

### 公网 IP 能力

请求 api.ipify.org，回显外部服务看到的当前请求出口；受 NAT、VPN 与代理影响。原版使用 IPv4 接口；网页独立实现时需区分浏览器出口和后端服务器出口。

### 电话能力

phonenumbers 在本地解析国家码，匹配编号计划、长度、号码模式和前缀元数据，给出地区描述、原始运营商（可用时）、可能时区、号码类型、标准格式及 Possible / Valid；默认地区 ID、描述语言印尼语。

### 用户名能力

把用户名填入 24 个 URL 配置、23 个不同平台名称，串行 GET，仅凭 HTTP 200 列出候选页面；并非搜索网页正文或全网搜索，同名账号不能证明同一身份。

### 模块与底层原理

拆成菜单调度、IP 查询、公网出口回显、号码解析、平台模板、HTTP 传输、结果呈现和依赖维护八个分析模块；下层是 IP 地理数据库、连接来源与 NAT、号码元数据及 URL / HTTP 规则。

### 使用场景

用于自己网络出口检查、已有日志的 IP 背景补充、国际号码格式整理、表单基础规则校验、自己公开用户名线索整理，以及学习 HTTP / JSON / API 适配；场景需要自行组合，原库没有业务闭环。

### 对后续开发的价值

帮助判断能查什么、数据从哪里来、结果能证明什么；可独立重写四个适配器并复用现成库。开发重点在可靠性、数据质量、平台判定、结果解释和持续维护。

### 可扩展方向

建议加入 HTTPS、超时与局部失败处理、IP 小数精度与成功状态校验、IPv6、可选号码地区、平台专用存在性规则、受控并发与缓存、多来源比较，以及可导出的来源 / 时间 / 判定依据记录。均为后续规划。

### 独立实现路线

先分别验证四项输入输出，再用浏览器、自己的后端和独立适配器整合，最后完善状态分类与维护。公网出口可由浏览器直查；跨站账号检测通常交给后端并处理 CORS、响应限制和失败状态。

## 引导图前的完整介绍

### 它是什么

把一个 IP、电话号码或用户名交给四个独立功能，获得背景信息或待核实链接。GhostTrack 自己写的是交互与调用逻辑，研究价值在于看清集成工具背后的真实能力来源。

### 能力与输入输出

已知 IP → 近似地区与网络归属；本机请求 → 公网出口；电话号码 → 号码规则与元数据；用户名 → 预设平台候选链接。电话有格式、类型和有效性等附加字段，用户名检测有 24 条配置、23 个平台名称。

### 模块与原理

菜单调度连接 requests 与 phonenumbers，再连接 IP 地理数据库、请求来源回显、本地号码元数据和平台网页。API 服务、库和数据各有自己的实现及维护成本，原库没有自建身份识别或实时定位系统。

### 使用价值

对我最有用的是建立准确的产品范围：网络出口和日志背景、号码格式校验、自己公开账号线索，以及 API 集成学习。能做出类似基础功能，准确度和可用性要靠数据、判定与工程维护。

### 复用与扩展

独立编写四个查询适配器，统一结果、来源、时间和失败状态；从号码与出口小工具起步，再加入 IP 背景与平台检测。逐步完善 HTTPS、超时、IPv6、地区选项、存在性规则、受控并发、缓存与导出。

## 四项能力：输入、输出与底层技术

### IP 归属查询

输入 IP 后，GhostTrack 请求 ipwho.is，再把接口返回的地区和网络信息打印出来。地图链接也由这些经纬度生成。

输入：已知 IP 地址。输出：国家 / 地区 / 城市、估计经纬度与地图、ASN / 网络组织 / ISP、时区等附加信息。

- **IP 地理信息数据库**：把 IP 或 IP 网段与地理位置、网络组织等信息关联起来。查询时取出数据库记录，不需要访问目标设备的 GPS。
- **服务商维护数据**：ipwho.is 文档描述了内存数据库、多来源数据聚合和持续更新。完整数据来源权重与定位算法没有在 GhostTrack 中实现；不能从这个仓库核实服务内部的完整流程。
- **近似位置与网络出口**：查询的是 IP 关联的位置。使用代理、VPN 或共享网络出口时，结果可能对应出口；移动网络的 IP 位置也不能直接代表手机当前位置。

可以说明：这个 IP 在数据库中关联哪个地区，以及属于哪个网络组织。

能力边界：不能确认设备的 GPS、具体住址或使用者身份。

具体局限：原版地图链接将经纬度转成整数，会额外丢失精度；还没有先检查接口 success 字段。

### 自己的公网 IP

GhostTrack 请求 api.ipify.org，读取返回的文本。这里不需要地理数据库，也没有进行 IP 位置推断。

输入：当前设备发出的网络请求。输出：请求来源的公网 IP。

- **网络连接携带来源地址**：网络通信需要来源与目的地址。服务端可以获取它收到的连接所使用的来源 IP，再通过 HTTP 响应返回。
- **NAT 与代理改变可见地址**：设备可能使用局域网地址，经过路由器或运营商 NAT 后对外使用公网地址。经过代理时，外部服务通常看到代理出口；多个设备可能共享出口。
- **谁发请求，查询的就是谁的出口**：命令行直接请求时，查到该运行环境的出口。若改成网页，浏览器直接请求与后端代请求的含义不同：后端请求 ipify 通常得到服务器的出口 IP。

可以说明：ipify 在这次请求中看到的公网来源地址。

能力边界：不能识别局域网中的具体设备，也不自动提供地理位置。

具体局限：原版使用 api.ipify.org 的 IPv4 接口；ipify 的 IPv6 和双栈接口属于服务能力，原版没有接入。

[固定源码 showIP() 170–176 行](https://github.com/HunxByts/GhostTrack/blob/a5cb8ad4c08acd803f166fb067b7dac724d6cb3d/GhostTR.py#L170-L176)

### 电话号码信息

GhostTrack 调用 phonenumbers。这个库是 Google libphonenumber 的 Python 移植版；安装后的规则和元数据可在本地查询，无需连接运营商定位系统。

输入：电话号码，建议携带 +国家码。输出：国家 / 号段地区描述、原始号段运营商（可用时）、可能的时区 / 号码类型、规则有效性 / 标准格式。

- **国家电话编号计划**：先解析国家码和本地号码，再用各地区的号码长度与号码模式规则检查格式、识别类型。编号元数据参考官方编号计划，并随库更新。
- **前缀匹配与地理元数据**：利用区号或号码前缀匹配预先整理的地区描述、运营商及可能的时区。不同国家和号码类型的覆盖程度不同，有时只能查到国家，或返回空信息。
- **规则有效性不等于真实启用**：Possible 通常检查长度是否可能；Valid 检查已知号码规则。两者都不能证明号码已分配、可接通或属于某个人。支持携号转网的地区，运营商信息通常指原始号段归属。

可以说明：号码在编号计划和号段数据中对应的地区、类型与格式。

能力边界：不能获知机主实名、手机当前位置，也不能判断是否已开通。

具体局限：原版默认解析地区是 ID（印度尼西亚），地理描述使用印尼语。其他国家号码应使用完整 +国家码，或在独立实现中允许选择解析地区。

[固定源码 phoneGW() 81–118 行](https://github.com/HunxByts/GhostTrack/blob/a5cb8ad4c08acd803f166fb067b7dac724d6cb3d/GhostTR.py#L81-L118)

### 同名账号线索

GhostTrack 把用户名填入预设的平台 URL，依次访问这些网页；只要 HTTP 状态码为 200，就把网址列为找到。它不搜索全网正文，也不核对账号是否属于同一个人。

输入：一个用户名。输出：预设平台上的候选账号网址、页面未找到或请求异常提示。

- **平台账号地址的命名规则**：为每个平台预先写好 URL 模板，例如平台域名后接用户名。平台改地址格式时，需要维护模板；这不是搜索引擎或身份数据库。
- **HTTP 请求与状态码**：客户端发送 GET 请求，服务器返回状态码与页面。200 只表示请求成功返回内容，内容也可能是登录页、错误提示或其他页面。
- **存在性判断与身份核实**：可靠的账号检测还需要识别页面正文、最终跳转地址和平台专门规则。即使账号确实存在，同名也不能证明多个平台的账号属于同一个人。

可以说明：这些预设网址值得进一步打开核实。

能力边界：不能保证账号存在、账号覆盖完整，或证明账号背后的身份。

具体局限：原版串行请求、没有设置超时，一次异常会中止这一轮查询。平台列表有重复配置，列表本身不能证明各站点当前仍可查询。

## 八个分析模块

### 菜单与函数调度

options 配置、装饰器与调用函数连接四项 CLI 功能；负责选择、输入与返回菜单。它组织流程，没有生成底层地理或身份数据。

### IP 信息适配器

IP_Track() 发送请求、解析 JSON、读取地理与网络字段并拼接地图链接。数据库维护与 IP 匹配发生在服务商一侧。

### 公网出口回显

showIP() 读取 ipify 文本响应。真正的观察者是接收连接的外部服务；请求从哪里发出，就测到哪里的公网出口。

### 电话号码解析

phoneGW() 调用本地库解析、格式化、校验并查询地区、运营商与时区。元数据随库发布，覆盖和时效取决于库版本与地区。

### 平台模板与检测

TrackLu() 内嵌网址列表、用户名格式替换和 200 判定。平台配置和检测逻辑耦合，需要人工维护；不是自动发现网站或搜索引擎。

### HTTP 传输

requests 承担 IP API、出口 API 和网页请求；原版没有设置超时。状态码、跳转、TLS、限流和网络错误会直接影响上层结果。

### 结果与错误呈现

终端彩色打印、字段展示、地图网址和异常提示。没有统一结构化结果、历史记录、证据评级或跨输入关联；用户名异常会终止本轮并跳过结果打印。

### 依赖与数据维护

requirements.txt 只列 requests、phonenumbers，未锁版本；外部接口、号码元数据和平台页面可分别变化。八模块是我们的分析划分，并非上游八个独立源码目录。

## 六类使用场景

### 自己的网络出口检查

检查当前网络请求使用哪个公网地址，比较不同网络或代理配置；只能说明出口，不能据此识别某一台内网设备。

### 已有日志的 IP 背景

对自己持有的访问或运维日志补充国家、ASN、ISP 等背景；原库不抓日志、不自动获得目标 IP，也不单独证明访问者身份。

### 国际联系人号码整理

用国家码和 E.164 统一联系人号码，检查号码类型、可能时区和地区描述；并不验证机主或号码是否仍在使用。

### 注册表单基础校验

把 Possible、Valid 和格式化作为基础输入校验；如需验证可达性或用户控制号码，另设计经过授权的验证码流程。

### 自己公开账号线索整理

用自己的常用用户名整理平台候选网址，再打开页面核对内容；不把候选当成账号存在结论或个人身份画像。

### 学习与轻量工具原型

从 HTTP、JSON、NAT、编号计划和页面判定学习模块化 API 集成；可做浏览器研究面板或运维小工具，再按需要增加业务流程。

## 对后续开发的六项价值

### 把需求说准确

把“追踪”拆成归属记录、网络出口、号段元数据和候选页面，让后续功能与宣传对应可验证的事实。

### 降低基础实现成本

已有 HTTP 库和号码库可以组合；无需先自建全球 IP 数据库或号码计划系统，先验证独立模块能否满足需求。

### 知道该投入哪里

简单调用容易完成；长期投入应放在来源质量、异常分类、平台规则、数据更新和用户对结果的正确解释。

### 形成可复用接口

四个适配器返回统一结构，网页、CLI 和其他内部工具都能消费；业务模块可按需装配，避免整套终端逻辑绑定。

### 让结果能够核查

保留来源、查询时间、输入规范化结果、判定方法与验证状态；把未知、失败、未找到、候选分别呈现。

### 看清授权边界

区分参考技术思路、复制程序、使用数据和调用服务的条件。独立重写接口层也仍需遵守所用依赖及服务规则。

## 四条独立实现路线

### 号码整理与校验组件

先独立接入 phonenumbers：提供地区选择、+国家码、E.164、Possible / Valid 和类型解释；适合联系人导入或表单基础校验。

最小交付：输入 → 标准号码 + 规则结果 + 元数据版本

### 浏览器网络出口小工具

由浏览器访问支持跨域的回显接口，显示客户端当前 IPv4 / IPv6 出口；后端出口另设单独入口，避免两者混淆。

最小交付：请求发起方 → 出口 IP + 观察来源 + 时间

### IP 背景补充面板

封装选定地理服务，检查 success 与失败信息，保留小数精度和来源；按需要做缓存或来源对照，解释数据库差异。

最小交付：已知 IP → 地区 / ASN / ISP + 近似性说明

### 公开账号候选整理器

先选少量自己需要的平台，维护 URL 与正文 / 跳转判定规则，在后端受控查询；保留候选、未知和人工核实状态。

最小交付：用户名 → 候选链接 + 判定依据 + 失败分类

## 三步推进顺序

### 第一步：四项分别验证

独立写输入校验和适配器；号码在本地运行，出口明确客户端 / 服务端，IP 选择来源，账号先做少量平台。记录正常、无数据、限流与异常样本。

### 第二步：整合自己的网页

浏览器 → 自己的后端 → 独立适配器 → 在线 API / 本地号码库 / 公开网页 → 统一结果。公网出口直查另行设计；跨站账号检测在后端处理，浏览器不能任意读取受 CORS 限制的页面。

### 第三步：验证与持续维护

先实现超时、局部失败、来源时间和未知状态，再完善缓存、平台规则、IPv6、导出和模块回归；用真实需求验证价值，不以“可以运行”代替结果准确性。

## 八项扩展方向（尚未实现）

### 01 · 可靠的传输与失败状态

改用 HTTPS，设置超时、重试上限和响应校验；单个平台失败不终止其他结果。区分网络异常、403、429、服务拒绝与未找到。

验收依据：受控故障样本可以返回局部结果和可解释状态。

### 02 · IP 结果精度与成功校验

保留经纬度小数，先检查接口 success / error 再读取字段；标明近似记录与提供商，地图保留原始精度。

验收依据：失败响应不会被当成位置，小数坐标不再截断。

### 03 · IPv6 与客户端 / 服务端分离

选择 IPv4、IPv6 或双栈回显入口，明确请求发起方；分别展示浏览器和服务器观察结果。

验收依据：用户能判断测到谁的出口，并识别网络不支持的情况。

### 04 · 号码国际化与元数据更新

允许选择默认地区和描述语言，优先完整国际号码；标注库版本，区分可能、规则有效、可达性及原始运营商。

验收依据：不同地区格式样本可重现，携号转网与空字段有解释。

### 05 · 平台专用存在性判断

清理重复和过期模板，检查最终 URL、正文或可用的官方接口；200 登录页应归为未知，避免强行给出存在结论。

验收依据：已知存在、已知不存在、登录和限流样本分别判定。

### 06 · 受控并发、缓存与任务进度

按平台和供应商限制设并发、队列与缓存时效，展示进度和取消；先定义查询范围，再扩展批量规模。

验收依据：失败可隔离、可取消，缓存记录来源和过期时间。

### 07 · 多来源与证据记录

按需求比较多个 IP 来源，并保留差异；统一返回输入、来源、观察时间、数据版本、判定规则与人工核实状态。

验收依据：结果可以追溯，来源冲突不会被包装成确定事实。

### 08 · 产品化与可维护规则

加入 JSON / CSV 导出、可更新平台规则、固定依赖与回归样本；根据用途设计最少保存、结果说明及清理机制。

验收依据：模块可独立升级，导出能复现解释，业务价值有实际使用验证。
