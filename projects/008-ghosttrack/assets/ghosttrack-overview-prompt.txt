【顶部】
GhostTrack 一图读懂
能力 → 实现 → 底层原理 → 后续开发价值
核心判断：这是一个 Python 命令行集成壳。核心能力来自现成服务、号码规则库和公开网页。
原库自己做：菜单交互、输入处理、函数调度、请求与库调用、结果打印。
四项查询相互独立；原库没有把手机号、IP 和账号关联成真人身份。

【矩阵栏目标题】
能力与输入 | 原库怎样调用 | 真正的底层技术 | 能得到什么 | 怎样理解边界

【矩阵第1行】
01 IP 归属
输入：已知 IP
IP_Track()
HTTP 请求 → ipwho.is → JSON
IP 地理信息数据库
IP / 网段与地区、网络组织的关联记录；服务商聚合和更新数据，完整内部算法不在此仓库。
国家、地区、城市、估计经纬度、ASN、运营商、时区
近似归属，不是 GPS。
VPN / 代理 / 共享出口会影响解释；不能确认住址或人的位置。

【矩阵第2行】
02 自己的公网 IP
输入：当前网络请求
showIP()
请求 api.ipify.org → 返回 IP 文本
IP 连接来源 + NAT / 代理
外部服务器看到请求来源地址，再回显给客户端；多个设备可共享同一出口。
这次请求使用的公网出口 IP
出口地址不是设备唯一身份。
后端代请求通常得到服务器 IP；不自动提供地理位置。

【矩阵第3行】
03 电话号码信息
输入：电话号码
phoneGW()
调用本地 phonenumbers
电话编号计划 + 号码模式 + 前缀元数据
国家码、长度与模式校验；号码前缀匹配地区、原始运营商和可能时区。规则随库更新。
国家或地区描述、类型、运营商信息、时区、标准格式、Valid / Possible
归属地区不是当前位置。
Valid 不等于已启用；携号转网后原始运营商可能不同；没有机主实名。

【矩阵第4行】
04 同名账号线索
输入：用户名
TrackLu()
URL 模板 → HTTP GET → 检查 200
平台账号命名规则 + HTTP 响应
按预设账号地址访问网页；200 只说明返回了内容。可靠检测还要检查页面内容与跳转。
预设平台的候选账号网址
200 可能是登录页或提示页。
同名不证明同一人；不搜索全网、不保证账号存在或平台覆盖完整。

【中下部】
对我后续开发的意义（以下为独立开发建议，不是原库已有功能）
1 能力判断
先问“数据从哪里来、结果能证明什么”，避免把查询归属误当实时追踪。
2 可复用技术
HTTP / JSON、API 集成、编号规则、前缀匹配、状态码与页面判定，都是可组合的通用模块。
3 能落地的工具
网络出口与日志背景查询、电话格式与基础校验、自己的公开用户名页面检查。
4 开发重心
基础版重在集成；可靠版重在数据质量、平台检测规则、错误处理和结果解释。
5 产品可信度
结果带上来源、查询时间与验证状态；把“候选”“未知”“失败”说清楚。
6 数据与授权
接口、数据库和程序代码分别看授权与使用条件；可以用现成库和接口独立实现。

【建议架构】
浏览器界面 → 自己的后端 → 独立查询适配器 → 在线 API / 本地号码库 / 公开网页
返回：统一结构化结果 + 来源 + 时间 + 判定说明
公网 IP 是例外：明确要查访客还是服务器；浏览器直接请求 ipify 可查自己的出口。
账号页面查询通常放后端；浏览器跨站读取受 CORS 限制。

【推进顺序】
先做四个独立查询模块 → 再整合网页与统一结果 → 最后提高稳定性与准确性
需要补齐：请求超时、HTTPS、失败处理、限流与缓存、平台专用检测、号码解析地区。
保留坐标小数；检查 API 成功状态；号码建议用完整 +国家码；不要只用 200 判断账号。

【源码与开放性】
GhostTrack：源码公开，固定版本未发现标准开源许可证。
phonenumbers：开源，Apache 2.0；ipify：官方提供开源实现。
ipwho.is：本项目通过在线接口使用，完整数据库与服务实现未随仓库提供。
